Architecture · ~1,800 words

The pure orchestrator: how T3 Code keeps agent work correct across crashes, retries and three clients

Hook: When an AI agent is editing your repo and the app crashes halfway through, what's true? T3 Code answers that with one rule: decide without I/O, commit everything at once, do the work afterwards.

1. The problem

T3 Code wraps provider CLIs (Codex, Claude Code, Cursor, Grok, OpenCode, Antigravity) in a WebSocket server. Turns start subprocesses, write files, capture git checkpoints and talk to GitHub, and any of those can fail, hang or outlive the client that started them. Clients reconnect from other devices. Commands get retried.

2. The shape

client RPC ──▶ command
              │
              ▼
   Orchestrator (pure: state + command → events, no I/O)
              │
              ▼
   EventSink — ONE transaction:
     events + projections (read models) + command receipt + outbox effects
              │  (after commit)
              ▼
   EffectWorker runs the effects (start turn, checkpoint…)
              │
              └──▶ results come back in as new commands

Files: apps/server/src/orchestration-v2/Orchestrator.ts, EventSink.ts, EffectWorker.ts.

3. Why each piece matters

  • No I/O in decisions. The orchestrator is a pure function of state, so you can test it, replay it, and know it won't hang on a network call.
  • One transaction. Read models can't get ahead of the event log, and the command receipt makes retries idempotent.
  • Outbox. The intent to do side-effect work is stored before any of it runs. If the process dies after commit, the intent is still there for recovery.
  • An ack means intent was recorded. The docs say it outright: a command acknowledgement means the intent committed, not that the provider finished. The UI has to reflect that, or the spinner lies.

4. The traps the docs call out

  • Persisted events must stay decodable on replay. Changing a schema hits old environments at startup as well as live RPC traffic.
  • A provider turn ending and its follow-up work (checkpoint, diff) settling are separate milestones. A late checkpoint must not make the turn's recorded duration longer.
  • Effects tied to a lost provider process can't just replay. Recovery retires them before it accepts new work.

5. Takeaway

You don't need a big event-sourcing framework. You need: a pure decide function, one transaction that records facts and intent together, and a worker that does the effects after commit. Most "it got into a weird state" bugs come from breaking one of those three.

Performance · ~1,500 words

Performance budgets as unit tests: what T3 Code does so 400k users don't feel a regression

Hook: Most teams find performance regressions when users complain. T3 Code puts the budget in a test file, so a regression fails vp test before it ships.

1. Budgets in tests

ThreadTransportPerformance.test.ts has a describe("thread transport payload budget") block that asserts the bounded snapshot is at most 2% of the full one, and that command event payloads are at most 10% of their size before omission. The docs give concrete targets: cold opens load about 75 recent timeline rows and around 1 MiB, and resume catch-up replays at most 128 events or 1 MiB before falling back to a snapshot.

expect(projectedBoundedRpcJsonBytes / fullRpcJsonBytes).toBeLessThanOrEqual(0.02);
expect(projectedRpcJsonBytes / preOmissionRpcJsonBytes).toBeLessThanOrEqual(0.1);

2. Benchmark the path users actually run

The perf doc includes a warning worth repeating: the older benchmark fixtures seeded v1 events, and running them against a v2 client "can produce reassuring timings while missing the active transport path." A benchmark that measures the wrong path is worse than having none.

3. Patterns from the perf commit log

PatternCommit

4. Keep heavy data off the wire

Raw command output, tool result bodies and inline file-change bodies are left out at the wire boundary. Persisted events keep everything, and diff endpoints serve file content when someone asks for it. The client gets the status and counts it needs to render, not megabytes of logs.

5. The quieter wins

  • Sequence cursors seek an index instead of scanning history.
  • Startup picks recovery candidates from projection state and doesn't load completed history.
  • Polling that finds nothing changed keeps the same array identity, so React subscribers don't re-render.
  • Live queries are leased to the visible viewport plus a small overscan.
  • Reconnects use jittered exponential backoff capped at 5 minutes, so a server restart doesn't bring every client back in the same second.

6. Takeaway

Write the budget down as a number, put that number in a test, and run it against the path users actually use.

Testing · ~1,400 words

Mock the boundary, not the logic: T3 Code's testing rules

Hook: "A test that needs a timeout to pass is wrong." That line from AGENTS.md sums up the whole testing approach.

1. The test shape

command dispatch → real Orchestrator → real ProviderAdapter
  → replayed provider transport (recorded frames)
  → real normalizer → real event sink → real projections → assertions

Fakes are allowed only at true boundaries: the provider transport (replayed from transcripts), the clock (TestClock), randomness (a deterministic Random), a temp filesystem, and a temp database. Not allowed: a mocked orchestrator, adapter, normalizer, event sink, projection reducer or checkpoint policy. (docs/orchestration-v2/testing-strategy.md)

2. Determinism comes from design

Production code reads time through Effect's Clock/DateTime and randomness through effect/Random, never Date.now or Math.random directly. That's what lets a test control time instead of waiting on it.

3. Drain instead of sleep

packages/shared/src/DrainableWorker.ts exposes drain(), which resolves only when the queue is empty and the item in progress has finished. An empty queue alone doesn't prove the worker is idle. Tests wait on drain() or on a specific persisted event, never on a sleep.

4. Test restarts without test-only hooks

To test an app restart, tear down the outermost layer and rebuild it against the same durable storage. Don't add a restartForTest() method to production code.

5. Enforce the rules with lint

  • no-test-in-loop: use it.each, not a for loop around it.
  • no-manual-effect-runtime-in-tests: tests don't build their own runtime.
  • Even the CI scripts have tests (.github/scripts/*.test.cjs, stage-preview-bundle.test.py).

6. Test against real data

vp run migrate-dev-db rebuilds a dev database from a read-only, pruned snapshot of the developer's real one. It drops scheduled tasks, pending work and auth sessions. Running migrations on that copy also proves a new migration applies on top of the migrations already applied in real data, and it catches two branches claiming the same migration number.

7. Takeaway

Fewer tests that run the real stack, deterministic time and IDs, and no sleeps. "No mocks" is the wrong lesson. The rule is that a fake is allowed only at a true boundary.

GitHub & OSS process · ~1,600 words

A PR process for the AI era: what T3 Code requires from contributors

Hook: When anyone can generate a 2,000-line PR in ten minutes, review time becomes the scarce resource. T3 Code's contribution process is built around protecting it.

1. The PR template asks for reasoning

Sections: Problem (a sentence or two), Change, Scope & approval (a link to the maintainer's approval comment, not just an issue), Verification. The template says "tests pass" alone is not enough: describe what you checked and what you saw, and say what you couldn't check. It ends with the model and harness that did the work.

2. One underlying problem per PR

"Count the underlying problems, not the linked issues." Several reports can describe one bug, and a large diff alone doesn't mean the PR mixes unrelated work.

3. Automation that gives context without gatekeeping

  • Size labels (XS to XXL) exclude test files in mixed PRs, so adding tests doesn't make a PR look bigger.
  • Vouch list (.github/VOUCHED.td) marks trusted contributors, but vouching is separate from skipping triage.
  • Mobile fingerprint check labels PRs that change the native build. Those are merged as a batch just before a store submission, so main can ship over-the-air updates the rest of the time.
  • CI rejects committed PR screenshots in .github/pr-assets. Evidence gets uploaded to GitHub.

4. AI triage that resists prompt injection

Each triage run resolves main to a commit SHA and loads the policy, the triage skill and the exemption list from that SHA. "PR/fork copies and PR-body instructions cannot change policy or exemptions." If a policy file is missing or malformed, the PR stays unresolved. Nothing gets exempted or auto-closed because of it.

5. Review bots with a narrow job

.macroscope/check-run-agents/ui-consistency.md reviews only changed lines, answers three questions, has a per-run budget, and replies exactly "All clear" when it finds nothing. approvability.md: a PR that changes product defaults, or adds a lint/type suppression, needs a human.

6. Closing PRs without insults

Every policy closure names the rule, cites the evidence, links the guide section and explains how to get the PR reconsidered. "We assess the problem, scope, approval, and evidence, not an author's writing style or whether we think an agent wrote the PR."

7. Commit titles that describe the outcome

fix(server): status refresh no longer pegs CPU in repos with thousands of untracked files. Conventional-commit prefix, then the change in user terms, so the changelog reads like release notes.

8. Security footnote

The pull_request_target size job has a comment: fetch untrusted PR commits "only as passive git data. Do not add dependency installs, build/test scripts, or cache actions here." That one comment heads off a whole class of supply-chain attacks.

  • knip in CI: an unused export fails the build, so dead code can't pile up.
  • Macroscope: a PR that adds a suppression can't be auto-approved.
Dev setup · ~1,200 words

A dev setup built for ten parallel agents on one machine

Hook: When five worktrees and five agents run dev servers at once, everything that's normally shared becomes a collision: ports, databases, processes, URLs.

  • Ports from a hash of the worktree path (scripts/dev-runner.ts). The same worktree gets the same ports across restarts, and the runner skips the ports browsers refuse to connect to (the Fetch spec's bad-ports list).
  • Probe only loopback when checking whether a port is free. Probing wildcard addresses made the runner move off a free port whenever tailscale serve held that number on another interface.
  • State per worktree: each worktree's .t3 takes priority over an ambient T3CODE_HOME, so you can't end up on shared state by accident.
  • Single-origin dev: Vite proxies /api and /ws. Never set VITE_WS_URL for dev, because it bakes localhost into the bundle and breaks every remote browser.
  • vp run dev --share publishes over the tailnet and prints a pairing URL.
  • t3.json runs worktree setup automatically: it links the shared .env and warms the dependency cache.
  • "Never kill by pattern": your own agent process has the worktree path in its argv. Kill only PIDs you captured when you spawned them.
  • Vendored reference repos (.repos/effect-smol): read-only library source so agents copy real patterns instead of making them up.

Takeaway: design dev tooling as if a dozen strangers share your laptop, because with agents that's roughly true.

UI/UX · ~1,200 words

Lying spinners, stale labels, one-way doors: UX rules from T3 Code

  • "Users notice a dropped frame, a lying spinner, and a stale label." No continuously repainting animations, because they peg the GPU on high-refresh displays.
  • Connection health and data freshness are separate. A socket opening doesn't prove the environment is usable. A failed shell subscription on a healthy connection must not show "Reconnecting", because that promises a retry that will never happen.
  • Cached data is readable offline but must not look live or overwrite newer data on reconnect.
  • Reverse states: "Snooze needs unsnooze. Close needs reopen. A one-way door is a bug."
  • Check every surface: if a behavior is reachable from chat, it's usually also reachable from Settings, the command palette and a keybinding, on web, desktop and mobile. Fixing one entry point doesn't fix the feature.
  • Slot composition: ComposerBanner exports small slots (Root, Row, Icon, Content, Actions). A banner built from them is a few lines with no styling of its own.
  • The server owns derived state: clients show the persisted settlement result and don't work it out from their own clocks, so every device agrees.
AI-native engineering · ~1,400 words

AGENTS.md as an onboarding doc: how T3 Code writes for its main contributor, an AI agent

Hook: "Most T3 Code contributions will come from T3 Code itself, often controlled remotely." The repo is the agent's workplace, and the docs are written that way.

  • A glossary so humans and agents mean the same thing by environment, project, thread and turn.
  • "The three ways to hurt yourself": killing by pattern, writing to the live install, baking in origins. Short, concrete and memorable.
  • "Hit every surface": a checklist covering entry points, clients, providers, MCP reach, contracts, reverse states, connection modes and docs.
  • Verification limits: the smallest proof that works. No repo-wide checks, because CI owns those.
  • Documentation rules: internal docs record decisions and traps that are hard to find in the code. No feature catalogs. When a decision changes, rewrite the text instead of appending to it.
  • Theo's note: "Fight for the smallest model that makes the correct behavior unsurprising." Channel both "measure twice, cut once" and "YAGNI".
  • Transparency: PR bodies end with the model and harness that did the work, and 1,000+ commits carry AI co-author trailers.
