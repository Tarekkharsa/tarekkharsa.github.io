How I Turned My Linux PC into a T3 Code Server I Can Use from Anywhere

A friendly, step-by-step guide, plus every problem I hit and how I fixed it.

What we're building

I have a powerful Linux PC at my desk. I wanted to use it from my MacBook and my Android phone, wherever I am, to run coding agents with T3 Code.

The plan was simple:

  • 🖥️ The PC runs T3 Code in the background, all the time.
  • 🔒 Tailscale connects my devices privately, so nothing is open to the public internet.
  • 💻📱 My laptop and phone connect to the PC through Tailscale.

The basic setup takes about 15 minutes. It took me a whole morning, because a few things went wrong. I've written them all down so you don't have to go through the same pain.

What you need:

  • A Linux PC (I used Ubuntu)
  • Node.js installed
  • A free Tailscale account, with Tailscale installed on the PC and on every device you want to connect from

Step 1: Install T3 Code on the PC

Open a terminal and run:

npm i -g t3
t3 service install

The first line installs T3 Code. The second sets it up as a background service, so it keeps running even when you close the app.

We also want it to start when the PC boots, even if nobody logs in:

loginctl enable-linger $USER

Check that it's working:

t3 service status

You should see Status: installed. ✅

Step 2: Make it reachable through Tailscale

T3 Code has Tailscale support built in. It gives your PC a private web address like:

https://my-pc.tailXXXXX.ts.net

Only your own devices on Tailscale can open it.

2a. Give yourself permission (one time)

By default, only the admin (root) can change these Tailscale settings. Allow your own user:

sudo tailscale set --operator=$USER

😬 If you skip this, you'll get: Access denied: serve config denied

2b. Turn on Tailscale in the T3 service

We'll add a small settings file. Doing it this way means T3 updates won't wipe it out.

mkdir -p ~/.config/systemd/user/t3code.service.d

cat > ~/.config/systemd/user/t3code.service.d/tailscale.conf <<'EOF'
[Service]
Environment=T3CODE_TAILSCALE_SERVE=1
EOF

systemctl --user daemon-reload
systemctl --user restart t3code

2c. Check it

tailscale serve status

You should see your https://...ts.net address. 🎉

💡 Tip: The very first time, it can take a few seconds to set up the HTTPS certificate. If the address doesn't load right away, wait a moment and try again.

Step 3: Connect your laptop and phone

On the PC, create a pairing code:

t3 pair --tailscale

It shows a QR code and a link. In the T3 Code app on your laptop or phone:

  1. Go to Add Environment → Remote link
  2. Paste the full link, or tap the 📷 camera icon and scan the QR code
  3. Tap Add environment

⏰ The code expires after 5 minutes. If you need more time, use t3 pair --tailscale --ttl 1h.

😬 Problem: "Transport error" when adding the environment

It looked like this:

Failed to fetch remote environment endpoint https://...ts.net/.well-known/t3/environment
(HttpClientError: Transport error ...)

This just means your device can't reach the PC. Check these, in order:

  1. Is Tailscale on? Open the Tailscale app on your laptop or phone and make sure it says Connected.
  2. On a Mac: Tailscale menu → Settings → turn on Use Tailscale DNS.
  3. Is the code still fresh? Make a new one if it's been more than 5 minutes.

😬 Problem: Android still won't connect

This one got me. Tailscale was connected, but my phone still showed the same error.

The fix: on your phone, go to Settings → Private DNS and set it to Off.

"Automatic" did not work for me, only Off. Private DNS stops your phone from finding the Tailscale address.

Step 4: Make sure your coding agents work

In the app, I saw this message:

❌ Could not start Codex CLI (codex).

There were two reasons.

Reason 1: Codex wasn't actually installed. Having the ChatGPT or Codex desktop app is not enough. You need the command-line tool:

npm i -g @openai/codex
codex login status

Reason 2: the background service couldn't find it. Background services only look in a few system folders, not where Node tools get installed. Add your folders to the same settings file from Step 2b:

cat > ~/.config/systemd/user/t3code.service.d/tailscale.conf <<EOF
[Service]
Environment=T3CODE_TAILSCALE_SERVE=1
Environment=PATH=$HOME/.local/bin:$(dirname $(which node)):/usr/local/bin:/usr/bin:/bin:/snap/bin
EOF

systemctl --user daemon-reload
systemctl --user restart t3code

💡 If you later switch Node versions with nvm, run this again so the path stays correct.

Step 5: Updating T3 Code (the tricky part)

😬 Problem: "This release requires a newer T3 Code service launcher"

I clicked Update from my Mac, and it failed with that message.

Why: my Mac app was on the nightly (beta) version, but the PC was on stable. Some updates can't be installed from another device; they have to be done on the PC itself.

The fix: run the update on the PC, using the same channel as your other devices:

t3 update --channel nightly --yes

(Use stable, preview or nightly, whichever your other devices use.)

😬 Problem: after updating, T3 wouldn't start at all

The log kept saying:

Service state is invalid or unsupported.

Why: I ran the update with the old version of the t3 command. It saved a settings file in an old format that the new version doesn't understand.

The fix:

  1. Open ~/.t3/runtime/service-state.json (make a backup copy first!)
  2. Change "protocol": 2 to "protocol": 3
  3. Restart the service and update your t3 command so this doesn't happen again:
systemctl --user reset-failed t3code
systemctl --user start t3code
npm i -g t3@nightly

✅ Golden rule: keep the PC, the t3 command and all your apps on the same channel.

Step 6: Make your PC act like a real server

A normal PC likes to go to sleep and wait for someone to press buttons. A server shouldn't. Here's what I changed.

Stop it from sleeping

sudo systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target
gsettings set org.gnome.settings-daemon.plugins.power sleep-inactive-ac-type 'nothing'

Turn off Wi-Fi power saving

It can make remote connections laggy or drop them.

printf '[connection]\nwifi.powersave = 2\n' | sudo tee /etc/NetworkManager/conf.d/wifi-powersave-off.conf

😬 Problem: after a crash, it got stuck at the boot menu

After an unexpected shutdown, Ubuntu shows a boot menu and waits forever for someone to press Enter. If you're not at home, your server is stuck offline.

The fix: tell it to continue on its own after 5 seconds:

echo 'GRUB_RECORDFAIL_TIMEOUT=5' | sudo tee /etc/default/grub.d/99-autoboot.cfg
sudo update-grub

Don't let Tailscale log you out

Tailscale logins expire after about 6 months. For your server, go to the Tailscale admin console, click ⋯ next to your PC, and choose Disable key expiry.

💡 Small tip: don't save helper scripts in /tmp. It's cleared on every reboot. I learned that the hard way.

Step 7: The mystery freezes (spoiler: broken hardware)

Everything was set up, but my PC kept freezing and restarting randomly. Here's how I found out why. The same steps work for any Linux machine that "just dies."

1. Check how it shut down

journalctl -b -1 -n 30

This shows the last lines from before the restart. A normal shutdown ends with shutdown messages. Mine just stopped mid-sentence, a sign of a hardware problem.

2. Put some load on it

sudo apt install stress-ng
stress-ng --cpu $(nproc) --verify --timeout 10m

Within seconds, random programs started crashing.

3. Look for a pattern

journalctl -k | grep -oE 'likely on CPU [0-9]+' | sort | uniq -c

My result:

4 likely on CPU 21

Every single crash happened on the same CPU core. Different programs, same core, so the core itself was broken. My CPU (an Intel 14th gen) is known for this problem.

4. Switch off the bad core

echo 0 | sudo tee /sys/devices/system/cpu/cpu21/online

I also added a small startup service so it stays off after every reboot. Then I tested again:

  • ✅ Every remaining core tested one by one: all passed
  • ✅ 15 minutes at full power, CPU and memory: zero errors, zero crashes

Losing one core out of 28 costs about 3–4% of performance. You won't notice it. But a broken core can get worse, so the real fix is replacing the CPU. Intel offers an extended warranty for affected 13th/14th-gen chips.
