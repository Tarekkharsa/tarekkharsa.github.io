Supply-chain attacks rarely arrive through code anyone reads. They arrive through a dependency bump in a lockfile nobody opens, or a postinstall script that runs on every developer's machine and every CI runner. This repo's policy is one line:

Treat npm dep and lockfile changes as reviewed code.

The engineering is in how each attack path gets closed.

Every path a dependency can take, and its gate

A silent upgrade

Exact versions only. Every direct dependency is pinned (no ^ or ~), and a script fails the check if one isn't.

Code at install time

No install scripts by default. Installs run with --ignore-scripts, locally and in CI.

A real need for a script

A three-entry allowlist for the install users get, each with a reason, like esbuild's "postinstall selects and verifies the platform-specific esbuild binary."

A lockfile change in passing

A pre-commit gate blocks any commit that stages the lockfile unless you confirm it with an environment variable.

The lockfile gate, in detail

package-lock.json is staged.

Review lockfile changes before committing:
  - confirm every new/updated package is intentional
  - confirm npm age gates were active for resolution
  - review any new lifecycle scripts in the dependency tree

Detected package version changes:
  - changed <package> <old> -> <new>

If this lockfile change is intentional, commit with:
  …_ALLOW_LOCKFILE_CHANGE=1 git commit ...
  1. Diff, don't guessIt compares the lockfile at HEAD with the staged one, entry by entry, and lists what was added, removed or changed.
  2. Quiet when nothing external changedChanges that only touch the repo's own workspace packages pass through, so the gate doesn't train people to ignore it.
  3. A checklist, not just a blockAge gates (refusing versions published too recently to have been vetted) and new lifecycle scripts are what most attacks rely on, so the hook asks about exactly those.

Agents can't slip a dependency change into an unrelated commit, and neither can humans.

Lists that can't rot

  • If an allowlisted install-script package disappears from the tree, the check fails and asks you to remove its entry.
  • A nightly npm audit fails on moderate advisories or worse. Accepting one requires naming the package and explaining why it doesn't apply, and the script warns about accepted entries that no longer match.
  • The same job runs npm audit signatures to verify registry signatures.
  • The curl installer pins every transitive dependency for users; plain npm install -g doesn't, and the README says so.

One dependency has a rule of its own: before updating undici, the HTTP client underneath Node's fetch, read its changelog and check whether anything affects the app.

Steal this

Make dependency changes loud. Pin exact versions, turn off install scripts and allowlist the few that need them with a reason, block lockfile commits unless someone says "yes, on purpose," and make every exception list fail when it goes stale.
