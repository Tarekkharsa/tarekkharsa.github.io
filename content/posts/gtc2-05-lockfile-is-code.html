Supply-chain attacks rarely arrive through code anyone reads. They arrive through a dependency bump in a lockfile nobody opens, or a postinstall script that runs on every developer's machine. This repo's agent guide has a one-line policy for that:

Treat npm dep and lockfile changes as reviewed code.

Then it backs the line up with tooling.

What that looks like

  • Exact versions only. Every direct dependency is pinned (no ^ or ~), and a script fails the check if one isn't.
  • No install scripts by default. Installs run with --ignore-scripts, locally and in CI.
  • A three-entry allowlist. In the pinned install that users get, exactly three dependencies may run install scripts, and each one has a written reason. esbuild's, for example: "postinstall selects and verifies the platform-specific esbuild binary."
  • An allowlist that can't rot. If an allowlisted package disappears from the tree, the check fails and asks you to remove its entry.
  • Pinned installs for users too. The curl installer pins every transitive dependency. Plain npm install -g doesn't, and the README says so.

A lockfile commit has to be on purpose

A pre-commit hook blocks any commit that stages the lockfile, and prints a review checklist instead:

package-lock.json is staged.

Review lockfile changes before committing:
  - confirm every new/updated package is intentional
  - confirm npm age gates were active for resolution
  - review any new lifecycle scripts in the dependency tree

Detected package version changes:
  - changed <package> <old> -> <new>

If this lockfile change is intentional, commit with:
  …_ALLOW_LOCKFILE_CHANGE=1 git commit ...

Agents can't slip a dependency change into an unrelated commit, and humans can't either. Changes that only touch the repo's own workspace packages pass through, so the gate stays quiet when nothing external changed.

And after it ships

  • A nightly npm audit fails on moderate advisories or worse. Accepting one requires naming the package and explaining why it doesn't apply.
  • The same job runs npm audit signatures to verify registry signatures.
  • One dependency gets a rule of its own: before updating undici, read its changelog and check whether anything affects the app.

Steal this

Make dependency changes loud. Pin exact versions, turn off install scripts and allowlist the few that need them with a reason, and block lockfile commits unless someone says "yes, on purpose." It costs minutes, and it's where supply-chain attacks actually land.
