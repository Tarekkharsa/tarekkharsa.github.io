At work I build a TanStack Start app whose server runs on Effect 4 and reads almost all of its content from a headless CMS over GraphQL. For a long time that GraphQL layer was gql.tada for typed documents, plus an Effect client we wrote by hand. This month we replaced both with effect/graphql, the GraphQL module that shipped in Effect 4.0.4, and its generator. The new client and the test transport are merged. The last step, moving every document to the generator, is in review as I write this.

This post covers why we moved, what we got, and how we did it in small steps without breaking the app along the way.

In short: gql.tada gave us types but no runtime check. effect/graphql decodes every response with a generated Schema, gives typed errors, middleware, a swappable transport for tests, and request batching. We moved in four steps, and the app worked after each one.

Where we started

gql.tada is great at one thing: you write a query in a template string, and TypeScript infers the result type from your schema. No codegen step, and good editor support.

import { graphql, type ResultOf } from "gql.tada"

const BookByIsbn = graphql(`
  query BookByIsbn($isbn: Isbn!) {
    book(isbn: $isbn) { id title publishedAt }
  }
`)

type Book = ResultOf<typeof BookByIsbn>

Around it we had our own Effect client: one query(document, variables) function that sent the request, mapped HTTP and GraphQL errors to our error types, handled partial results, cached, and recorded metrics. About 40 documents and 200 call sites went through it.

Why we moved

  1. The types were a promise, not a check. At runtime the client received JSON and cast it to ResultOf<typeof Doc>. When the CMS changed a field, nothing failed at the boundary. We found out later, as an undefined somewhere in a page.
  2. A 31,424-line type cache in git. To keep the editor and tsc fast, gql.tada writes a cache of every document's types. Ours was over 31,000 lines, and if it went missing, tsc failed with TS2589 (type instantiation is excessively deep).
  3. TypeScript 7. gql.tada and its language-service plugin need the classic compiler API. The native TypeScript 7 issue was closed as not planned, so we were running two TypeScript versions side by side.
  4. We owned too much client code. Errors, retries, partial results, test mocks: all hand-written, and all things a library could own.

What effect/graphql gives us

1. Operations are values, and results are decoded

You keep queries in .graphql files. The generator, @effect/graphql-generator, turns each one into a TypeScript file with a Schema for every selection and an operation value:

// graphql.config.ts
import { defineConfig } from "@effect/graphql-generator/Config"

export default defineConfig({
  schema: "./schema.graphql",
  documents: ["documents/**/*.graphql"],
  scalars: { Isbn: "./scalars.ts#Isbn" }
})
import * as Context from "effect/Context"
import { GraphQLClient, GraphQLGroup } from "effect/graphql"
import { BookByIsbn } from "./documents/BookByIsbn.graphql.ts"

class Library extends Context.Service<Library>()("Library", {
  make: GraphQLClient.make(GraphQLGroup.make(BookByIsbn))
}) {}

const book = Library.use((library) => library.BookByIsbn({ isbn }))
// Effect<BookByIsbn.Result, GraphQLClientError, Library>

The result is decoded with the generated Schema, not cast. If the CMS sends something the query didn't promise, you get a DecodeError at the boundary, with a path, instead of a broken page later. Custom scalars like Isbn decode to your own branded types.

2. One error type with the details you need

Every failure is a GraphQLClientError with a tagged reason, so mapping it to your own errors is one switch:

switch (error.reason._tag) {
  case "ResponseError":  // the server answered with GraphQL errors
  case "TransportError": // the request failed: network, timeout or HTTP status
  case "DecodeError":    // the answer didn't match the query's Schema
}

Errors carry the HTTP status and headers, and a response error knows its retryAfter and whether it isRetryable. With { partial: true } a call returns { data, errors }, so one failing field doesn't take down a whole page.

3. Middleware, in one place

Spans, metrics and logs live in one GraphQL middleware attached to every operation, instead of being spread through the client. It sees the operation name and the outcome, which is what our dashboards group by.

4. A transport you can swap

The client talks to a GraphQLProtocol service. In production that is GraphQLProtocol.layerHttp({ url }) on top of Effect's HttpClient, so our existing retry and timeout policy still applies. In tests it is a few lines:

const scripted = (fixtures: Record<string, unknown>) =>
  Layer.succeed(GraphQLProtocol.GraphQLProtocol, {
    execute: (request) =>
      Effect.succeed({ body: { data: fixtures[request.operationName ?? ""] } }),
    subscribe: () => Stream.empty
  })

Fixtures still go through the real decode and the real middleware. When we switched our mocked backend to this, 10 fixtures failed to decode: 8 were missing a __typename that the real CMS always sends, and 2 had timestamps in the wrong unit. The old mock had been happily returning invalid data for months.

There is also GraphQLClient.layerTest, where handlers return values directly. It's handy, but it skips decoding and middleware, so we use the scripted protocol for anything that should behave like production.

5. Batching for free

GraphQLResolver.aliased turns many lookups into one request, each lookup as an aliased copy of the query:

const library = yield* Library
const Books = GraphQLResolver.aliased(library.BookByIsbn).pipe(RequestResolver.batchN(20))
const getBook = GraphQLResolver.request(Books)

yield* Effect.forEach(isbns, (isbn) => getBook({ isbn }), { concurrency: "unbounded" })
// 4 lookups, 1 POST

We had one hand-built "aliased query" string for exactly this. It's the next thing to go.

How we moved

We split the move into steps that each left the app working, so each PR could be reviewed and shipped on its own.

  1. Upgrade Effect to 4.0.4 and pin it exactly. The GraphQL module is marked experimental, so it may change in a patch release.
  2. Swap the transport, keep the signature. Our query(document, variables) function stayed the same, so 0 of the 200 call sites changed. Inside, it now builds an effect/graphql operation and maps GraphQLClientError to our existing error types in one function. Every cache key changed once, because the key is now a hash of the printed document.
  3. Replace the mock with a scripted GraphQLProtocol keyed by operation name, and fix the 10 fixtures it caught.
  4. Move to the generator, one area of the app at a time (member pages, search, content pages, and so on), then remove gql.tada.
    • ResultOf<typeof Doc> became Doc.Result.
    • VariablesOf became Doc.Variables.
    • Fragments became typeof Fragment.Type, and every readFragment() call disappeared.
    • A graphqlgen --check step in our gates fails when a generated file is out of date.

The generator step touched 195 files: about 12,000 lines added and 38,500 removed, most of the removed lines being the old type cache. The generated code is about 7,000 lines, and it's real code that runs, not just types.

What bit us

  • Decide what "success" means yourself. With partial results, a response body can be passed through even on an odd status. Our own status helper called a 3xx "ok", and a review caught that a redirect with a data body could be cached as valid. We now require an explicit 2xx, with a test for 300, 302 and 304.
  • partial: true is not "anything goes". A null in a non-null field still fails the whole result, as it should. Check how your server propagates nulls before you switch.
  • Don't call the protocol directly. GraphQLProtocol.execute skips the middleware, so your metrics and spans disappear. Go through the client.
  • The API moved during the release. Between the preview builds and 4.0.4, request headers became Headers.Headers, and the generator started emitting Schema.Opaque classes. Pin exact versions while it's experimental.

Should you move?

If you already use Effect on the server, I think yes. You get runtime decoding, typed errors and a test transport for the price of a generator step. If you don't use Effect, gql.tada is still a great way to get typed documents with no build step. You just have to remember that the types are a promise, not a check.
