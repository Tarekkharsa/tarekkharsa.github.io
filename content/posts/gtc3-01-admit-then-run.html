In most agents, pressing Enter does two things at once: it adds your message to the conversation and starts the model. That's fine until something goes wrong in between. The process restarts, the request retries, or you send a second message while the agent is mid-task. Which message did the model see, and in what order?

This repo's rewrite splits the two apart.

Admission and promotion

A prompt first lands in a durable inbox, a session_input table. That's admission: the input is accepted and replayable, but the model hasn't seen it yet. Later, a runner promotes it: one atomic step consumes the inbox row and appends the visible user message to the conversation.

sessions.prompt({ id?, sessionID, prompt, delivery?, resume? })
  -> supplied ID inserts one durable inbox row when absent
  -> exact reuse returns the same admission receipt
  -> reusing one message ID for another session, prompt,
     or delivery mode fails
  -> resume false admits only

Retries are safe by construction: send the same prompt with the same ID twice and you get the same receipt back, not a duplicate message. Reuse the ID for something different and it fails loudly instead of guessing.

Steer or queue

Because admission and promotion are separate, "what happens to a message sent mid-task" becomes an explicit rule instead of a race:

  • Steer (the default): promoted at the next safe boundary before a model call, while the current task continues.
  • Queue: waits until the session would otherwise go idle, then promotes one queued input, and decides again before promoting the next.

Clients can show pending input from the admission event, before it's part of the conversation.

What isn't durable, on purpose

The running part, a drain, is deliberately not a stored entity: "A Session Drain has no durable identity or transcript boundary." Interrupting stops the current process's work but keeps the inbox rows for a later run, and interrupting an idle session is a no-op. Recovery reasons from what's durable (prompts, history, provider attempts, tool state), not from an invented "execution" record.

The agent guide spells this out as an invariant: "Keep durable prompt admission separate from model execution."

Steal this

Put a durable inbox between "the user sent it" and "the model sees it." Make prompt IDs idempotent, make steer and queue explicit delivery modes, and don't persist the parts that are only coordination.
