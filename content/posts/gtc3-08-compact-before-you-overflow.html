Many agents handle long conversations reactively: send the request, get "context length exceeded" from the provider, then squash everything into a paragraph and retry. The summary is vague, the exact error string and file path from an hour ago are gone, and the agent starts guessing.

This repo's rewrite compacts before the request stops fitting, and it treats the summary as a structured hand-off.

▶

Try it: when compaction kicks in

add turns, change the model window, make the summary fail

Before every model call, the estimated request is compared with the window minus room for the reply. Over it, older turns become a summary and the newest ~8k tokens stay word for word. If the summary fails, nothing changes.

When to compact

estimate({ system, messages, tools }) > context - max(maxOutputTokens, buffer)
  1. Estimate the whole requestSystem prompt, messages and tool definitions, before calling the provider, not after it refuses.
  2. Reserve room for the replyThe model's output budget or a 20,000-token buffer, whichever is larger. A request that fits but leaves no room to answer is still a failure.
  3. Check the summary fits tooIf the summarization prompt itself wouldn't fit in the window minus its own output budget, it doesn't try.

What to keep, and how to summarize

Recent turns, verbatim

Walking back from the newest message, about 8,000 tokens are kept word for word, so the current task's details survive exactly.

Older turns, summarized

Everything before that goes to a summary with a fixed template: Objective, Important Details, Work State (Completed, Active, Blocked), Next Move, Relevant Files.

Preserve exact file paths, symbols, commands, error strings, URLs, and identifiers when known.

Tool results inside the summarization input are trimmed to 2,000 characters each, so one huge output can't crowd out the conversation being summarized.

Compacting again

The second compaction merges with the first, with explicit rules instead of "summarize this":

The <prior-summary> is discarded after this: anything you do not carry into the new summary is lost. [...] Where they conflict, the conversation wins.

Objectives, constraints and decisions are carried forward even if the recent conversation doesn't mention them; finished work moves from Active to Completed.

Failure changes nothing

The start of a compaction is recorded durably; progress is live-only. The switch to the summary happens only from a completed summary event. A failed or empty summarization returns without cutting over, the full history stays stored, and after a successful one the runner continues the original pending turn with a fresh context baseline.

Steal this

Check before every call whether the whole request still fits with room for the reply. Summarize only older turns, into a fixed template that preserves exact identifiers, keep recent turns verbatim, and only switch over once the summary exists.
