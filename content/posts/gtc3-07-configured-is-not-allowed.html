Here's a common shape for "turn off provider X": an enabled_providers list, a disabled_providers list, and some code that checks both while it loads provider config. It works until a company wants to forbid a provider that a developer has perfectly valid credentials for. Now "is it configured?" and "is it allowed?" are tangled into one setting.

This repo's v2 replaces those lists with a separate idea: policy.

Two different questions

A provider can be correctly configured and have valid credentials while policy still denies its use.

  • Config describes endpoints, options and model overrides. It answers "how do I use this?"
  • Policy answers "may I use this?" It doesn't configure anything, and "policies do not make unusable resources usable."

The whole evaluator

A statement is an effect (allow or deny), an action and a resource, both with wildcards. Evaluation is one line:

statements.findLast(
  (s) => Wildcard.match(action, s.action) && Wildcard.match(resource, s.resource),
)?.effect ?? fallback

The last matching statement wins. There's no "more specific pattern beats a wildcard" rule: "A specific resource does not automatically beat a wildcard resource. Written/evaluation order controls the result." So "deny everything except Anthropic" is exactly two lines in that order:

{ "effect": "deny",  "action": "provider.use", "resource": "*" },
{ "effect": "allow", "action": "provider.use", "resource": "anthropic" }

Each caller passes its own default. Provider use defaults to allow, so a user with no policy sees no change at all.

Built to grow, but only a little

The vocabulary is meant to cover more actions later, like plugin.load or mcp.connect, with user policy overriding repository policy and, eventually, organization policy overriding both. The non-goals are written down just as clearly: no conditions, no principals, no approval prompts.

Steal this

Keep "is it configured?" and "is it allowed?" in separate layers. Make policy ordered statements where the last match wins, so anyone can predict the result by reading top to bottom.
