Two different questions

Config: how?

Endpoints, options and model overrides.

Says nothing about permission.

Policy: may I?

Ordered allow/deny rules with wildcards.

"Policies do not make unusable resources usable."

A provider can be correctly configured and have valid credentials while policy still denies its use.

Order decides, not specificity

There's no "the more specific rule wins" magic: "A specific resource does not automatically beat a wildcard resource. Written/evaluation order controls the result." You can predict any answer by reading the rules top to bottom, which is what the demo above does. Each caller passes its own default; provider use defaults to allow, so people with no policy see no change.

Small on purpose

The same vocabulary is meant for more actions later, like plugin.load or mcp.connect, with user rules overriding repository rules. The non-goals are written down too: no conditions, no principals, no approval prompts.

Steal this

Keep "is it configured?" and "is it allowed?" in separate layers. Make permission an ordered list where the last match wins, so anyone can predict the result by reading top to bottom.
