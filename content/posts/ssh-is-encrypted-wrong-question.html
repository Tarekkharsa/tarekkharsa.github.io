Theo, who created T3 Code, posted this today:

Someone tried to tell me t3 code is bad and their terminal phone app was better because "ssh is encrypted"

— Theo (@theo), Oct 9, 2026

It's a great prompt, because the argument sounds reasonable. SSH is encrypted, and it's one of the most battle-tested protocols we have. So is WhatsApp. I still wouldn't give WhatsApp a root shell on my laptop.

"It's encrypted" answers a question nobody asked. Here's why, and the four questions I now ask about any "it's encrypted, so it's secure" claim.

The two setups

  • Phone terminal: an SSH app on the phone (Termius, Blink and friends), an SSH key stored on it, and coding agents running in tmux on the server.
  • T3 Code: a T3 Code server on the same machine, the T3 Code app on the phone, connected over Tailscale, T3 Connect, or SSH.

Both are legitimate. I've used both.

First, the strongest version of their point

SSH deserves its reputation: decades of scrutiny, strong defaults, key-based login, and it's already on every server. If your rule is "the only thing I expose is sshd", that's a defensible rule. Fewer moving parts is a real security property, and I'd never argue otherwise.

Encryption answers one question out of four

Securing remote access comes down to roughly four questions:

QuestionWhat answers it
Can someone on the network read or tamper with my traffic?Encryption
Who is allowed to connect?Authentication
What can they do once they're in?Authorization
How do I take access back?Revocation

"SSH is encrypted" only answers the first row. It's like picking a car because the seatbelts work: true, important, and also true of every other car in the lot. Which brings us to row one.

Row one is a tie

T3 Code's recommended ways to connect are all encrypted:

RouteEncrypted?
TailscaleYes: WireGuard end to end, plus HTTPS through Tailscale Serve. This is my home-server setup.
T3 ConnectYes: HTTPS through a managed Cloudflare tunnel. T3's relay brokers the pairing but never receives your session token.
SSHIt literally is SSH: the desktop app can connect to a machine over SSH, start the server there and forward the port for you.
Plain LAN pairing (t3 serve --host <ip>)No: plain HTTP.

That last row is the fair part of the criticism. Direct LAN pairing is plain HTTP, and T3 Code's own docs say so. On your home network that's a small risk. On café or hotel Wi-Fi, don't use it; use Tailscale. If the argument had been "don't pair over plain HTTP on public Wi-Fi," I'd have agreed completely.

The threat that actually happens: a lost phone

Breaking modern encryption is hard and rare. Losing a phone, having it stolen unlocked, or installing a sketchy app is common. So run the realistic scenario: someone else has your phone.

With the phone terminal

An SSH key on that phone usually means a full shell as your user: every file, every credential in ~/.config, your git push access, rm -rf. The good news: when the thief runs rm -rf ~, it will be end-to-end encrypted. 🔐 SSH can restrict a key (command=, restrict, from= in authorized_keys), but almost nobody does, because it's manual and easy to get wrong. So in practice the key is all-or-nothing.

Taking it back means deleting that key from authorized_keys on every machine it can reach. And if your app syncs keys to its cloud vault for convenience, that's one more place the key lives.

With T3 Code

Each device pairs separately and gets its own session:

  • Scoped. Pairing can narrow permissions but never widen them. A device can be read-only (--scope orchestration:read): it sees threads but can't start or steer agents. Ordinary pairing never grants permission to create new pairings or manage access.
  • Revocable per device. Settings → Connections lists every session. Revoke the lost phone; nothing else is touched.
  • Bound to the device, over T3 Connect. Those sessions are tied to a key held by the device (DPoP), so a copied token alone isn't enough.
  • Agents are fenced too. In Supervised mode, the agent asks before running commands or changing files, and the approval shows up on your phone.

To be fair, a T3 Code device with full permissions is powerful too: it can start an agent in Full access mode, which can run any command. The difference is that you can choose less, per device, and revoke it cleanly. With SSH you could too, but it's work, so in practice almost nobody does.

That's least privilege, the genuinely hard part of security, and it's where the two setups actually differ.

Usability is a separate argument

Running Claude Code in tmux over SSH works. tmux keeps sessions alive across disconnects, and a terminal is the most honest UI there is. Some people love it, and that's fine.

T3 Code's case is about the experience: approvals as buttons, diffs you can actually read on a phone, a notification when an agent needs you, many threads across many machines, history that survives restarts, and switching between Codex, Claude and others mid-conversation. Those are real reasons, but they're product reasons, not security reasons. Keep the two arguments apart; mixing them is how "SSH is encrypted" ends up sounding like a reason to pick a whole product.

They're not mutually exclusive either: T3 Code has a terminal panel, and it can connect over SSH.

The lesson: encryption is a property of the pipe

Security is a property of the whole system. "It's encrypted" is the "it compiles" of security: necessary, nice to hear, and wildly insufficient. Next time someone says "X is secure because it's encrypted," ask:

  1. Who can connect? (authentication)
  2. What can they do once they're in? (authorization)
  3. How do I take it back? (revocation)
  4. What happens when a device is lost? (the threat that actually happens)

Encryption tells you the pipe doesn't leak. It tells you nothing about what comes out the other end. A sealed envelope is great; it doesn't matter much if you mailed it to the burglar.

What I actually run

T3 Code on my home PC, reachable only over Tailscale, with plain-HTTP LAN pairing off. My phone is paired with the permissions it needs, and I'd revoke it in one click if I lost it. SSH is still there for the days I want a raw shell.

Use the tool that fits. Just know which question each one answers.
