"Make the tests faster" usually goes like this: someone tries a few things, the suite gets a bit quicker or doesn't, and nobody remembers what was tried. Six months later, someone tries the same things again.

This repo keeps a lab notebook instead: one Markdown file with a goal, a metric and a table of hypotheses.

The setup

  • Goal: "Speed up the test suite without reducing coverage or hiding failures."
  • One primary metric, printed as a parseable line: METRIC test_suite_seconds=<median wall clock seconds>.
  • Two scripts: one benchmarks the full suite, one profiles files to find the slowest.
  • Signals to watch, written down up front: repeated setup, long sleeps, serial integration tests, fixture costs, test globs that pull in unrelated work.

Every hypothesis is a row

Timeout test waits the full      optional timeout,      12.949s  8.305s  keep
production timeout               25ms in the test
Obsolete 1s sleep after a sync   removed the sleep      10.270s  9.433s  keep
write

Targeted changes are measured as the median of several runs, because single runs were noisy enough to mislead.

The dead ends stay in the book

There's a separate "Dead Ends" table for changes that didn't pay off, each with a reason: removing a cleanup step gave an improvement "within noise" and the cleanup was a safety net; a shorter timeout "changed the error shape"; shorter sleeps looked faster on the first run and slower on verification. That table is what stops the next person, or the next agent, from trying them again.

Coverage beats seconds

The full suite went from 225s to 187s. Then a safety review restored prompt and SDK coverage that some wins had cut, and it settled at 202s. Giving 15 seconds back was the right call, and the notebook shows why.

Steal this

Run performance work as experiments: one metric, one row per hypothesis with before, after and a decision, and a list of dead ends. It works just as well when an agent is doing the experimenting.
