Try it: crash in the middle

the same requests against a naive handler and an outbox

A naive handler saves the order and then sends the email. If it crashes in between, the email is lost and nothing remembers it was owed. With an outbox, the intent to send is committed together with the order, and a worker sends it after the commit, even after a restart.

The pattern

  1. Decide, with no I/OA pure function turns (state, command) into events. It never touches the network, the filesystem or a subprocess, so you can unit-test it, replay it, and it can't hang on a slow API while holding a lock.
  2. Commit facts and intent togetherOne database transaction writes the events, the read models the UI reads, a command receipt, and the outbox: a record of side effects that still need to run.
  3. Act after commitA worker picks up outbox rows and does the slow, failure-prone work (start the agent, take a git checkpoint). Results come back as new commands, through the same loop.

What the one transaction buys you

Read models can't lead

They commit in the same transaction as the events, so the UI never shows something the log doesn't have.

Retries are idempotent

A replayed command finds its receipt and returns the same result, instead of doing the work twice.

Crashes keep intent

If the process dies right after commit, "start the agent" is already saved in the outbox.

I/O can't corrupt state

The slow part runs outside the transaction, so a timeout can't leave half-written rows.

The consequence most apps get wrong

A command acknowledgement means the intent committed, not that the work finished.

If your UI treats "request accepted" as "done", you ship a lying spinner. Here, "accepted", "agent running" and "follow-up work settled" are separate states. A late checkpoint isn't even allowed to stretch the recorded duration of the agent's turn.

Two traps the docs call out

  • Your schema has a past. Every stored event must still decode on replay. A schema change affects every old database on its next startup, not just the newest client.
  • Not every effect can replay. Work tied to a provider process that died is retired during recovery, before new work starts.

Steal this

You don't need an event-sourcing framework. You need a pure decide step, one transaction that records facts and intent together, and a worker that does the I/O afterwards. Most "it got into a weird state" bugs come from breaking one of those three.
