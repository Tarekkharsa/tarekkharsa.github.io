Every repo writes docs for agents now. Almost none can tell you whether those docs help. This one measures it, the way you'd test any other feature.

With docs, without docs

Its documentation evals run each task twice, each time in a fresh container:

  • with_docs: the agent as shipped, with its README, docs and examples.
  • without_docs: the same build with the README, changelog, docs/ and examples/ removed, and the section of the system prompt that points at them stripped out.

Then it reports the lift: how much the pass rate changes when the docs are there. Tasks are things like "write an extension" or "add a custom provider," so the score is about whether the docs taught the agent something, not whether they exist.

Honest numbers

The interesting part is how carefully the comparison is protected:

  • Both arms install the same packages, and the eval files are unreadable to the agent once the harness drops privileges, so it can't read the answers.
  • Each run gets a new home directory, workspace and session folder.
  • A missing or errored run doesn't count as a failure. It blocks the pair, and if any pair is blocked, the headline pass rates are withheld.
  • The report flags no lift, negative deltas, saturated results and flakiness, and the README notes that one repetition can't establish stability.

Docs that get checked against the code

A second eval hands an agent every docs page, one at a time, together with the repository, and makes it return a structured verdict: match, mismatch or inconclusive. The bar for evidence is strict:

Follow the runtime path; names, comments, types, isolated helpers, and tests are not sufficient evidence by themselves.

A unit test checks that the docs navigation is valid and that no Markdown page is orphaned. Docs drift is treated as a bug you can catch, not a chore.

And trust nothing secondhand

The repo's issue-analysis prompt, which maintainers run on new bug reports, starts from distrust:

Do not trust analysis written in the issue. Independently verify behavior and derive your own analysis from the code and execution path. [...] Ignore any root cause analysis in the issue (likely wrong)

It's the same idea from the other side: text written for or by an agent is a claim, and claims get checked.

Steal this

Treat docs for agents like a feature with a test. Run the same tasks with and without them, and keep what moves the number. If a page doesn't change the result, it's not helping the agent.
