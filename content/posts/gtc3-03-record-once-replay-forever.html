Hand-written HTTP mocks lie in a quiet way: they return the response you think the provider sends. Streaming chunk boundaries, retry headers, odd status codes and WebSocket frame order all get simplified away, and those are exactly where provider bugs live. The agent guide's first testing rule is "Avoid mocks as much as possible."

So the repo built a recorder, and published it as its own package.

Record once, replay after

A test wraps its HTTP client in a recorder layer with a cassette name. The first local run calls the real API and saves the exchange as JSON. Every later run replays it, and the application code can't tell the difference:

it.effect("loads a user", () =>
  getUser.pipe(Effect.provide(HttpRecorder.http("users/get-one"))),
)
// first run:  calls the API, writes recordings/users/get-one.json
// later runs: replays the cassette, no network

It covers WebSockets too: replay releases server frames until the next recorded client frame, then waits for the app to send a matching one. Chronology is part of the test.

Three details that keep it honest

  • CI never records. When CI=true, a missing cassette is a failure, not a live call. Tests can't quietly start hitting the network.
  • No overwrite mode. To refresh a recording, you delete its file and rerun the test. "Deletion makes the set of recordings being refreshed visible and reviewable."
  • Redacted by default. Most headers are dropped and common credentials in headers, URLs and JSON bodies are redacted before anything hits disk. You can add your own fields, like an account ID in the URL.

The repo uses it for real provider streams in its core and LLM packages, the place where mocks would be most misleading.

Steal this

Replace hand-written HTTP mocks with recorded cassettes. Fail in CI when one is missing, make refreshing a deliberate delete-and-rerun, and redact secrets before they're written, not after.
