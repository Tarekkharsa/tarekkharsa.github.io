Here's a performance bug that no profiler flags and no test catches. You import one small function:

import { reduceLaneSnapshot } from "@scope/agent-core";

The function is one file, 6 KB. But the package's entry point is a barrel (an index.ts that re-exports everything), so Node evaluates the whole graph behind it: 106 files. A server in the same repo loaded 112 files just to list some file headers.

The fix, and the guardrail

The fix was ordinary: narrow subpath exports, so callers can import ./harness/session instead of the barrel. That took one module graph from 42 files to 19, and the server from 112 files / 98 MB to 28 files / 69 MB.

The interesting part is what stops it from coming back. A script runs on every commit, walks the value-import graph of each declared entry point, and fails when it grows past a budget or reaches a forbidden file:

"./models": {
  maxFiles: 15,
  forbid: ["providers/", "models.generated.ts", "index.ts", ...],
},

Its header explains the idea better than I can:

Entry points are cost contracts. [...] one stray export * can silently make a narrow entry drag an entire barrel [...] and nothing fails until someone measures a process.

It paid for itself immediately

The first run caught two regressions hiding in plain sight:

import { type Usage } from "./types";

That looks type-only, but it isn't. Only import type { Usage } is erased completely; the inline type form still emits a runtime import of the module. Through a barrel, that's the whole package.

Why count files, not milliseconds

  • It's deterministic. A file count doesn't flake on a slow CI machine.
  • It's cheap. It only reads import statements, nothing runs, so it fits in the pre-commit check instead of a nightly benchmark.
  • It points at the cause. The failure lists the files the entry reached, so you see the bad import, not just "startup got slower".

The same repo checks that some of its packages still bundle for the browser, for the same reason: what a module drags in is part of its interface.

Steal this

Budget what a module drags in, not just how fast it runs. A file count and a forbidden-path list per entry point catch the stray export * and the import { type X } that nobody notices in review.
