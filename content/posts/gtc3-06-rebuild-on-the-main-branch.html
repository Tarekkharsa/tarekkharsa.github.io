The classic way to build a version 2 is a long-lived branch. It starts clean, falls behind, and becomes a merge nobody wants to do. This repo tried that: its 2.0 branch ends at a commit called "2.0 exploration", from April. Everything on it has been merged, and it's now 4,760 commits behind the default branch.

The real rewrite happens on the default branch, next to v1, and it's engineered so both can be live at once.

Two versions, one database

  1. Clear names, side by sideNew code lives in places like specs/v2, test/v2, the v2 plugin and SDK folders and a session/v2 page in the app, while v1 keeps shipping releases.
  2. A bridge between themA shadow bridge publishes prompts made through v1 as the same v2 events, so v2's projections see the conversation during the transition.
  3. Disposable on one side onlyExperimental v2 events, projections and inputs may be reset when their shape changes. Canonical v1 session, message and part rows are always preserved.

A dated log of every contract change

A schema changelog records each v2 change to the database, durable events, projected messages, HTTP API or generated SDK: 28 dated entries, each with why it changed and whether consumers or stored data need compatibility handling. Commit messages for those changes are meant to carry the same summary.

Reset experimental V2 events, projections, inputs, Context Epochs, and synchronized workspace state while preserving canonical V1 session, message, and part rows.

Durable event names carry a version number, like session.next.prompt.admitted.1, and changes to unpublished experimental events are logged with what happens to data already stored.

Port nothing by default

The legacy config schema was reviewed field by field: 12 keep, 14 remove, 13 redesign, each with a reason.

Removed: logLevel

"No config consumer exists and logging initializes from CLI input."

Removed: server

Location config is loaded after the server is already running, so it could never take effect.

The old config.json filename isn't supported in v2, and design options that lost are kept in the specs as history. The planning doc is refreshingly honest about the goal: "ok we need to work towards a launch of v2 so we can get out of this rebuild phase".

Steal this

Grow the next version on your main branch behind clear names, bridge the old writes into the new model, version every durable contract, log every change with its data impact, and make every legacy setting earn its way in.
