The classic way to build a version 2 is a long-lived branch. It starts clean, falls behind, and eventually becomes a merge nobody wants to do. This repo tried that. Its 2.0 branch ends at a commit called "2.0 exploration", from April. Everything on it has been merged, and it's now 4,760 commits behind the default branch.

The rewrite actually happens on the default branch, next to v1.

v2 lives beside v1

New code sits in clearly named places, like specs/v2, test/v2, v2 plugin and SDK folders and a session/v2 page in the app, while v1 keeps shipping releases. A bridge publishes prompts made through v1 as v2 events, so v2 sees them during the transition. The planning doc is refreshingly honest about why:

ok we need to work towards a launch of v2 so we can get out of this rebuild phase

A dated log of every contract change

A schema changelog records every v2 change to the database, durable events, projected messages, HTTP API or generated SDK: 28 dated entries. Each says why the contract changed and what existing data needs:

Reset experimental V2 events, projections, inputs, Context Epochs, and synchronized workspace state while preserving canonical V1 session, message, and part rows.

Experimental v2 data is allowed to be thrown away. v1 data never is.

Port nothing by default

The config review goes through the legacy schema field by field, and each one gets a verdict: 12 keep, 14 remove, 13 redesign, each with a reason. logLevel is removed because "no config consumer exists". The server settings are removed because location config loads after the server is already running. The old config.json filename isn't supported in v2.

Design options that lost are kept too, marked as history, so the next person can see what was considered.

Steal this

Grow the next version on your main branch, behind clear names, instead of on a branch that drifts. Keep a dated log of every contract change with its compatibility story, and make every legacy setting earn its way into the new version.
