Most tools grow by adding features to the core. This one grows by refusing to. Its contributing guide opens with the rule:

If your feature does not belong in the core, it should be an extension. PRs that bloat the core will likely be rejected.

That's easy to write and hard to live by. What makes it real is the next part.

First-party features are plugins too

MCP support, a code-execution mode and tool search all ship inside the product. But none of them are wired into the core. They're built-in extensions, using the same extension API anyone else gets:

export const builtInExtensions = [
  { name: "llama.cpp",   factory: llamaExtension,      builtin: true },
  // Replaceable: an extension that registers `codemode`, `tool_search`,
  // or `/mcp` takes over instead of running alongside the built-in one.
  { name: "codemode",    factory: codemodeExtension,   replaceable: true, builtin: true },
  { name: "tool-search", factory: toolSearchExtension, replaceable: true, builtin: true },
  { name: "mcp",         factory: mcpExtension,        replaceable: true, builtin: true },
];

Install a third-party MCP extension that registers /mcp, and the built-in one steps aside: it stops reading its config and stops connecting servers. Remove the extension and the built-in one comes back. Nobody had to add a setting called "use the other MCP".

Features it doesn't ship

The README says it plainly: it skips features like sub-agents and plan mode. Instead, there are 79 example extensions, including subagent, plan-mode, permission-gate and sandbox. The suggested way to get a missing feature is to ask the agent to build it as an extension, or install a package that does it your way.

Even hook points cost something

The guide doesn't treat extensibility as free either:

Even hook points for extensions however should be well considered and discussed to avoid adding unmaintainable bloat and complex interactions.

A small core with a hundred ad-hoc hooks isn't small. Every hook is API surface someone has to keep working.

Why this works

  • The API gets tested by its own authors. If MCP can be built as a plugin, so can the next protocol.
  • Opinions become optional. You can disagree with how the built-in MCP works without forking the project.
  • The core stays reviewable. Less code in the middle means fewer interactions to reason about.

Steal this

Build your own features on your public plugin API, and let users replace them. If a first-party feature can't be written as a plugin, your API is missing something, and you just found it.
