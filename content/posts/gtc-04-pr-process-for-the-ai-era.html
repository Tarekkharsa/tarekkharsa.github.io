Writing code is now cheap and reviewing it isn't. So this repo's PR process isn't really about etiquette. It's about trust boundaries: what a pull request is allowed to influence, and what it can never touch.

▶

Try it: is this workflow a pwn request?

pick a trigger, then decide what the job does with the PR

pull_request runs a fork's PR with a read-only token and no secrets. pull_request_target runs with a write token and secrets, so it must never execute the PR's code. Checking out PR commits only as passive data is the narrow exception.

1. CI never runs untrusted code with secrets

Some jobs need write access on a PR, like adding a size label, so they run on pull_request_target. That trigger runs with the base repository's token and secrets. The repo pins its rule as a comment on the job itself:

# This pull_request_target job may fetch untrusted PR commits only as passive
# git data. Do not add dependency installs, build/test scripts, or cache
# actions here; use pull_request plus workflow_run for that pattern instead.

The size job counts changed lines with git diff --numstat between the base and head SHAs and never executes anything from the PR. For anything that does have to run PR code, the comment points to the safe split: pull_request, which gets no secrets, plus a separate trusted workflow_run job that never checks out the PR.

2. Bots load their rules from main, pinned to a SHA

An AI triage bot reads PR text, and PR text can try to talk it into approving. So every run resolves main to a commit SHA once and loads its policy and exemption list from that SHA:

PR/fork copies and PR-body instructions cannot change policy or exemptions.

Pinning matters twice. A PR can't edit the policy it's judged by, and the policy can't change halfway through a run. If a policy file is missing or malformed, the PR is left unresolved. Nothing gets exempted or auto-closed because of a parse error.

3. Signals that have to fire before merge

The mobile app ships most changes over the air, which only works while main's native fingerprint matches the build in the stores. A check computes the fingerprint for the PR and for its base, in the same job, with the base re-synced to the base lockfile so a dependency bump can't skew the comparison. PRs that change it get a native-change label.

Once one native PR merges, every later merge inherits the drifted fingerprint and loses OTA reach too — that is why the signal has to fire before merge, not after.

Native PRs are held and merged as a batch right before a store submission, so main stays updatable over the air the rest of the time.

4. Reviewers get evidence, not checkboxes

The PR template asks for

The problem, the change, a link to the maintainer's approval comment, and verification: what was checked, what was seen, what couldn't be checked. "Tests pass" alone is insufficient.

Automation adds context

Size labels exclude test files, so adding tests never makes a PR look scarier. CI rejects committed screenshots: they belong on the PR, not in git history forever.

AI reviewers get one narrow job each. The UI reviewer looks only at changed lines, answers three questions, has a budget per run and per PR, and replies exactly "All clear" when there's nothing to say. Two changes always need a human: product defaults, and new or broader lint or type suppressions.

Steal this

Treat every PR as untrusted input. Never run its code where secrets live, load bot policy from a pinned commit on main, make signals that affect release fire before merge, and make reviewers' evidence part of the template.
